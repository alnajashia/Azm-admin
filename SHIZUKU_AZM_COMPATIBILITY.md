# SHIZUKU ↔ AZM COMPATIBILITY — Reverse engineering focused on Azm's actual needs
Written 2026-11-11 at Ahmed's direction: RE of Shizuku *as it relates to Azm*, and an explicit list of every Azm change that would be needed — **no Azm file is modified by this document; each change below needs Ahmed's permission first.**

Sources: Shizuku clone HEAD `b844bc4` (see SHIZUKU_ARCHITECTURE.md, BINDER_PROTOCOL.md) and Azm v1.0.6 source in `~/workspace/dominater-rebuild/project` (audited directly).

## 1. Mechanism-by-mechanism verdicts

| # | Shizuku mechanism (source) | How Azm uses it today (exact) | Verdict for an Azm-native replacement |
|---|---|---|---|
| 1 | Native starter `manager/jni/starter.cpp`: CLASSPATH=manager APK, fork/setsid, `app_process` → `rikka.shizuku.server.ShizukuService`, process `shizuku_server`, UID = caller's (2000 via ADB, 0 via root), no setuid anywhere | Not used by Azm directly — it is how the *Shizuku app* starts its server, which Azm then talks to | **Reimplement smaller**: same app_process pattern, Java starter class is enough (Shizuku's own user-service path proves a Java starter works); native starter only adds kill-old-server/cgroup/SELinux niceties |
| 2 | Binder discovery: server pushes its binder to the manager app via ContentProvider `moe.shizuku.privileged.api.shizuku`; clients receive it via their own `ShizukuProvider` (Azm manifest declares `rikka.shizuku.ShizukuProvider`, authority `${applicationId}.shizuku`) | Azm's `Shizuku.getBinder()` — the provider in Azm's manifest is what delivers the server binder into Azm's process | **Reimplement with own identity**: Azm Admin's provider authority `io.github.alnajashia.azmadmin.binder` delivers the binder to clients that call it; Azm's own ShizukuProvider declaration is deleted (see M3) |
| 3 | Client registration `attachApplication` (AIDL 17, wire 18): server records uid→packages (packages-for-UID is the ownership proof), ClientRecord, death recipient | Implicit — the Shizuku API library does it for Azm on first call | **Keep the pattern**: same proof (Binder calling UID → packages via IPackageManager) works for any server; it is Android's own identity mechanism, not Shizuku IP |
| 4 | Authorization: `requestPermission` (AIDL 14) → server starts manager's `RequestPermissionActivity` → Allow = **persistent**, Deny = one-time → `dispatchPermissionConfirmationResult` (104) → config file `/data/user_de/0/com.android.shell/shizuku.json` (schema v2, batched writes) + runtime-permission mirroring | `ShizukuGateway.requestPermission(911)`, `checkSelfPermission()`, permission-result listener; Flutter polls state every 500 ms | **Keep the flow, tighten the record**: same UX (ask → user approves in the manager app → persistent). Replacement stores (package, uid, **signing-cert SHA-256**) at approval and re-verifies all three per call — Shizuku stores package/uid flags only |
| 5 | Shell execution `IShizukuService.newProcess` (AIDL 7) → `IRemoteProcess` (stdin/out/err, waitFor, exit value) running as server UID | `ShizukuRunner` — the backbone of all 13 Azm commands (settings/pm/dpm/dumpsys) | **Replace with typed server-side operations**: the server itself runs the same binaries via ProcessBuilder for the 5 known operation groups. Azm never needs arbitrary commands; a free shell is attack surface Azm doesn't use |
| 6 | Binder wrapper `ShizukuBinderWrapper` → server `transactRemote`: parcel = token + target binder + code + (v13) flags + original parcel; server replays it under `clearCallingIdentity()` — **no validation of target/code/args** (verified, BINDER_PROTOCOL.md) | `ShizukuProvisioning.withShizukuDevicePolicyManager`: wraps `IDevicePolicyManager` so `setActiveAdmin` / `setDeviceOwner` / `forceUpdateUserSetupComplete` execute as shell UID | **Replace with one dedicated server operation**: server calls IDevicePolicyManager directly (it already runs as shell UID) inside `provisionDeviceOwner`. Same result, no generic proxy — this is the single riskiest Shizuku mechanism and Azm uses it for exactly 3 related calls |
| 7 | State APIs: `getVersion` (2), `getUid` (3), `checkSelfPermission` (15), `pingBinder`, `isPreV11` | `ShizukuGateway.statePayload` → channel `getShizukuState` → Dart `ShizukuStatus{state, version, uid, preV11}` | **Keep equivalents** (version, uid, authorization state). Drop `preV11` semantics — meaningless for a v1-native protocol; keep the field in the payload for wire compatibility, always false |
| 8 | Config persistence & recovery: server config in shell's device-encrypted storage; `BootCompleteReceiver` restarts server after reboot only for root, or ADB mode on API ≥33 with WRITE_SECURE_SETTINGS | Azm's cold-start repair `restoreStuckUserSetupComplete` depends on the server being alive at app start | **Keep honestly**: an ADB-started server cannot reliably self-restart after reboot (Android forbids it); the manager app must show "server stopped — start again" truthfully. Root mode may auto-restart |

## 2. Shizuku subsystems Azm does NOT need (drop entirely)
User services (`addUserService`/`attachUserService`, AIDL 11/101) · rish shell terminal · system properties (9/10) · `getSELinuxContext` (8) · app hiding flags (103/105/106) · `dispatchPackageChanged` (102) · Shizuku's own manager home/API-demo UI · multi-client general authorization for arbitrary apps (Azm Admin v1 authorizes Azm — other clients only by the same explicit approval flow).

## 3. The 5 operation groups that ARE the whole replacement surface
1. `provisionDeviceOwner` — user_setup_complete bypass/restore + setActiveAdmin/setDeviceOwner (direct DPM in server, `dpm` fallback), verified by owner re-read.
2. `grantWriteSecureSettings` — `pm grant`, verified by re-check.
3. `setAccessibilityEnabled` — settings get/put, verified by re-read.
4. `getDiagnostics` — dumpsys account / pm list users / dpm list-owners, parsed server- or client-side.
5. State + authorization — version/uid/state, request flow of row 4.

## 4. AZM MODIFICATIONS — permission list (nothing applied yet)
Minimal variant (recommended): **keep every Flutter/Dart wire name identical** so Dart logic is untouched.
- **M1 — Kotlin, replace 3 files**: `shizuku/ShizukuGateway.kt`, `ShizukuRunner.kt`, `ShizukuProvisioning.kt` → Azm Admin client-backed equivalents with the same internal functions/signatures `PrivilegedChannelHandler` already calls. (Optionally rename the package `shizuku/` → `azmadmin/` — cosmetic, same change size.)
- **M2 — Gradle**: remove `dev.rikka.shizuku:api:13.1.5` + `:provider:13.1.5`; add the Azm Admin `:client` library (project/AAR dependency) in `android/app/build.gradle.kts`.
- **M3 — AndroidManifest**: delete the `rikka.shizuku.ShizukuProvider` declaration (authority `${applicationId}.shizuku`).
- **M4 — Kotlin, small edits in `PrivilegedChannelHandler.kt` + `DeviceOwnerManager.kt`**: the `installShizuku` channel method currently opens Shizuku's Play page (`DeviceOwnerManager.installShizuku`) — it must instead open Azm Admin (Play page/intent when published, or a "not installed" state). Error-code names `SHIZUKU_*` in `ChannelErrors.kt` can stay as-is (wire-compatible) or be renamed with matching Dart changes.
- **M5 — Dart, texts only (no logic)**: `lib/ui/setup_screen.dart` user-visible strings that say "Shizuku" (install prompt, "start the Shizuku server" guidance) → "Azm Admin". `lib/data/privileged_channel.dart` needs **zero** changes in the minimal variant: `ShizukuState/ShizukuStatus`, `getShizukuState`, `requestShizukuPermission`, and the `SHIZUKU_` error prefix all keep working because the Kotlin side keeps the same payload.
- **M6 — Setup UX copy**: the `notRunning` guidance changes meaning — from "open Shizuku and start its server" to "open Azm Admin and start its server". Strings only, same state machine and 500 ms polling.

Full-rename variant (not recommended now): renaming channel methods/events (`getShizukuState`→`getAzmAdminState`, event types `shizukuBinderReceived`→…) additionally touches `privileged_channel.dart` and `setup_screen.dart` logic for zero functional gain; can be done later as cleanup.

**Explicitly NOT modified in any variant**: all other Kotlin (Device Owner enforcement, accessibility service, recovery gate), all other Dart, signing, versioning scheme, and the repo/release flow. Azm's runtime blocking never depended on Shizuku and does not change.
